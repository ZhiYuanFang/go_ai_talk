## Context
- 当前语音对话流程是 STT -> DeepSeek -> TTS，但 DeepSeek 仅接收当前轮转写文本，缺少设备级历史上下文。
- 新需求要求按设备号维持临时会话历史，实现连续对话；不要求持久化，服务重启后丢失可接受。
- 该能力需要与现有并发限制、超时与错误处理策略协同，且不能引入内存无界增长风险。

## Goals / Non-Goals
- Goals:
  - 基于 `deviceNo` 提供设备级多轮上下文拼接。
  - 采用进程内临时缓存，不引入数据库或外部缓存依赖。
  - 通过 N 轮上限与 TTL 控制内存规模，并支持配置。
  - 保持现有 STT/TTS 处理路径不变，仅增强 DeepSeek 消息构造与状态管理。
- Non-Goals:
  - 不提供跨实例共享会话（多副本之间不保证上下文一致）。
  - 不提供重启恢复或历史追溯。
  - 不引入新的前端会话管理协议。

## Decisions
- 缓存键：使用请求体 `deviceNo` 作为唯一会话键。
- 缓存形态：进程内 map（线程安全）存储每设备消息列表与最后活跃时间。
- 消息策略：
  - DeepSeek 请求按顺序组织：`system`（可选）+ 历史轮次 + 当前 `user`。
  - 请求成功后再写入本轮 `user` 与 `assistant`；失败不写入，避免脏历史。
- 边界策略：
  - 每设备仅保留最近 N 轮（默认 10，按 user+assistant 成对裁剪）。
  - 设备会话 TTL 默认 30 分钟；超过 TTL 视为新会话。
  - 可选全局最大设备会话数（建议默认 1000），超过后按最久未活跃淘汰。
- 可观测性：记录命中/过期/淘汰计数日志或指标（不记录敏感明文内容）。

## Risks / Trade-offs
- 单实例内存状态简单高效，但在多实例部署下会话不共享；该行为符合“临时缓存、可丢失”约束。
- 同设备高并发可能导致上下文竞态；需保证读写原子性，并在必要时按设备粒度串行化更新。
- 过小 N 或 TTL 会降低上下文连续性，过大则增加内存与 token 成本；通过配置平衡。

## Migration Plan
1. 新增配置项并提供默认值，不启用额外依赖。
2. 增量实现会话缓存与 DeepSeek 消息拼接逻辑。
3. 补充单测/并发测试并回归现有语音链路。
4. 灰度观察缓存命中率与错误率，按需调整 N/TTL。

## Open Questions
- 无（需求方已确认：`deviceNo` 通过请求体传入；缓存采用“每设备最近 N 轮 + TTL”策略）。
