## Context

当前实现中，账号主体实际绑定在 `wx` 表，网关签发 access 时将 `wx.id` 写入 JWT `sub`，下游通过 `X-Internal-Wx-Id` 识别主体。现有流程偏微信 OAuth，历史规格文档仍包含 `unionid` 必填与旧头语义，和已上线实现存在偏差。

本次目标是在不拆分账号主键、不新增独立用户表的前提下，将“用户名密码”并入既有模型，并补齐历史页面 `nickname` 展示。约束如下：
- 统一主键仍为 `wx.id`；
- `unionid` 可为空（用户名体系可独立存在）；
- 一个微信只能绑定一个用户名账号（1:1）；
- 密码必须密文（哈希）存储；
- 服务边界不变：history/voice 不直查 device 表，画像扩展仍走 device 契约。

## Goals / Non-Goals

**Goals:**
- 在 `wx` 表完成用户名注册、登录、绑定微信、绑定设备、改密、微信下创建用户名六类能力。
- 用户名登录链路可由 gateway 聚合签发与现有一致的 access/refresh。
- 明确冲突语义：用户名唯一、微信唯一绑定、账号状态可判定。
- 扩展历史画像读取契约，增加 `nickname` 字段并在页面展示。
- 同步修订受影响 specs，消除旧语义（如强制 unionid）的规格漂移。

**Non-Goals:**
- 不新增独立用户账号表。
- 不改造 JWT 主体字段（`sub` 仍是 `wx.id`）。
- 不引入微信多账号绑定到同一用户名账号。
- 不在本变更引入短信/邮箱找回密码、MFA、风控平台。

## Decisions

### D1：账号实体统一继续使用 `wx` 表

- 决策：用户名密码、微信绑定、设备绑定统一归属 `wx` 行；`wx.id` 为唯一账号主键。
- 原因：与现有 access token 语义完全兼容，避免会话体系二次迁移。
- 备选：新增 `account` 表再映射 `wx`。被拒绝，原因是迁移成本高、回滚复杂、短期收益低。

### D2：密码存储采用单向哈希（bcrypt）

- 决策：`wx.password` 存储 bcrypt 哈希串，登录/改密只做哈希比对。
- 原因：满足“密文入库”且避免可逆密钥管理问题。
- 备选：AES 可逆加密。被拒绝，原因是泄漏面更大、密钥轮换复杂且不符合密码校验最佳实践。

### D3：账号状态机与绑定规则

- 决策：定义三种账号状态：
  1) 用户名账号（`user_name`+`password`，`unionid` 可空）
  2) 微信账号（`unionid`，用户名未设置）
  3) 绑定完成账号（两者均有）
- 规则：
  - `user_name` 全局唯一；
  - `unionid` 全局唯一（允许空）；
  - 一个 `unionid` 仅能归属一个 `wx.id`；
  - 已绑定微信的账号不可再绑定其他微信。
- 备选：允许一个微信绑定多个用户名。被拒绝，因违反用户已确认约束。

### D4：接口分层

- 决策：
  - device-service 新增/扩展业务接口完成用户名能力；
  - gateway-app 增加用户名聚合登录接口，签发逻辑复用现有 `SignAccess` + refresh 存储。
- 原因：保持“device 负责账号事实、gateway 负责令牌”的职责边界。
- 备选：device 直接签 token。被拒绝，因破坏现有架构职责与统一鉴权入口。

### D5：`nickname` 来源与边界

- 决策：`nickname` 由 device 画像契约提供，history 通过既有远程/本地适配获取并透传，前端页面直接展示。
- 原因：符合“跨服务数据访问必须走契约”约束，避免 history 直查 device 库表。
- 备选：history 直接查询 `wx.user_name` 或其他表。被拒绝，违反服务边界规范。

### D6：向后兼容与错误语义

- 决策：保留微信登录、设备号登录原路径；新增用户名路径并统一错误码语义（参数错误/冲突/认证失败/未找到）。
- 原因：保障存量客户端兼容，降低灰度风险。
- 备选：替换旧登录路径。被拒绝，风险过高。

## Risks / Trade-offs

- [Risk] 现网 `wx` 表唯一索引与“`unionid` 可空”约束在不同 MySQL 配置上表现差异 → Mitigation：在迁移脚本中显式验证索引策略并在上线前执行数据体检。
- [Risk] 用户名大小写/空白处理不一致导致“伪冲突”或重复账号 → Mitigation：统一规范化（trim + 小写比较策略）并在接口层与存储层双重校验。
- [Risk] 改密后并发登录窗口可能出现旧密码短暂可用 → Mitigation：改密成功后可选失效该账号 refresh token，强制重新登录。
- [Risk] `nickname` 口径不清（来自 `user.baby_name` 还是 `wx.user_name`）造成前后端认知偏差 → Mitigation：在规格中明确字段来源与优先级，避免歧义。
- [Trade-off] 使用 bcrypt 会增加少量 CPU 成本 → 可接受，换取密码安全与实现简洁。

## Migration Plan

1. **数据库前置检查**
   - 确认 `wx.user_name`、`wx.password` 列已存在；
   - 校验 `user_name` 唯一索引与 `unionid` 唯一索引策略支持 `unionid` 为空。
2. **服务端发布顺序**
   - 先发布 device-service（新增用户名接口、哈希校验、绑定语义）；
   - 再发布 gateway-app（用户名聚合登录）；
   - 最后发布 history 页面与画像返回扩展。
3. **灰度与回滚**
   - 灰度期间保留旧微信登录链路；
   - 若异常，网关可临时下线用户名聚合入口，device 保持兼容；
   - 回滚时不删除已写入哈希密码数据，仅关闭入口。
4. **验收**
   - 覆盖 6 类接口正反例；
   - 校验 token `sub` 仍为 `wx.id`；
   - 校验历史页 `nickname` 展示与性别共存。

## Open Questions

- `nickname` 业务定义最终来源：优先 `wx.user_name` 还是沿用 `user.baby_name`，或二者组合兜底？
- 用户名规范是否强制为 `[a-z0-9_]{4,32}`，是否允许中文？
- 用户名登录失败是否需要统一返回“用户名或密码错误”（防枚举）？
- 改密是否强制要求旧密码，是否允许微信已登录态下免旧密改密？
