## Context

系统当前处于“单体与微服务并行”的过渡阶段，运行时仍包含可选后端开关（Redis vs memory、MQ enabled vs disabled）与降级分支。这些分支会掩盖依赖故障并增加领域代码复杂度。与此同时，gateway 仍承载部分兼容期领域能力，而独立服务入口（如 history-service）已存在。

本变更目标是统一基础设施依赖与服务边界：Redis 和 RabbitMQ 成为强依赖；voice/device 领域能力拆分为独立服务；gateway 收敛为流量与策略层。

## Goals / Non-Goals

**Goals:**
- 将 Redis 设为 voice、device、history 全域唯一缓存后端。
- 将 RabbitMQ 设为跨服务唯一事件通道，并对必需发布路径执行“发布失败即阻断”。
- 在服务启动阶段引入 Redis/RabbitMQ 显式依赖校验与 fail-fast 机制。
- 按数据归属与领域边界拆分 voice、device 为独立可部署服务。
- 将 gateway-service 收敛为鉴权、路由、策略与元数据透传的边缘层。
- 统一缓存键、事件命名、依赖故障处理等运行时规范。

**Non-Goals:**
- 本阶段不引入多中间件插件化框架。
- 本阶段不承诺所有接口零感知平滑迁移。
- 本阶段不恢复关键依赖的进程内兜底降级分支。

## Decisions

1. **Redis-only 缓存决策**
   - 决策：移除缓存后端切换与内存兜底分支。
   - 理由：单后端可降低分支复杂度并提升行为一致性。
   - 备选方案：保留 memory 降级作为韧性策略。
   - 不采纳原因：会掩盖依赖异常，导致多实例状态不一致，并持续拉高维护成本。

2. **RabbitMQ-only 事件通道与发布阻断语义**
   - 决策：移除 MQ 可选开关；必需事件发布失败时阻断请求并返回错误。
   - 理由：跨服务流程需要可验证的事件投递语义以保证业务正确性。
   - 备选方案：发布失败仅记录日志并继续流程。
   - 不采纳原因：会造成静默丢失，削弱事件一致性保障。

3. **启动失败即终止（Fail-fast）策略**
   - 决策：服务启动时必须完成 Redis/RabbitMQ 连通性与拓扑校验；失败即终止启动。
   - 理由：把隐性运行时故障前移为显性部署故障，便于快速定位。
   - 备选方案：懒加载依赖，首个请求时再探测。
   - 不采纳原因：会把故障暴露到用户请求路径，增加排障难度。

4. **服务拆分与 gateway 收敛**
   - 决策：voice/device 领域逻辑迁移至独立服务，gateway 仅保留边缘编排能力。
   - 理由：提升部署独立性、团队边界清晰度与横向扩展能力。
   - 备选方案：继续在 gateway 保留部分领域实现并做轻量远程调用。
   - 不采纳原因：耦合难以下降，无法形成清晰领域边界。

5. **统一运行时约定**
   - 决策：统一 Redis key 命名/TTL 策略与 RabbitMQ exchange/routing-key 规范。
   - 理由：防止命名漂移，降低联调错误并提升可观测性一致性。
   - 备选方案：各服务各自定义规范。
   - 不采纳原因：会造成运维碎片化和幂等/重试行为不一致。

6. **抽离统一基础设施适配层（cache-kit / event-kit）**
   - 决策：抽离 `cache-kit` 与 `event-kit`，业务服务仅通过适配层接口访问 Redis 与 RabbitMQ，禁止直接调用底层客户端。
   - 理由：统一超时、重试、错误语义、日志、指标与追踪能力，避免各服务重复实现并减少行为漂移。
   - 备选方案：保留各服务直接调用 Redis/MQ，仅通过代码规范约束。
   - 不采纳原因：规范难以长期执行，重复代码会回流，故障语义和可观测性难统一。

## Risks / Trade-offs

- **[依赖故障影响放大]** Redis/RabbitMQ 强依赖会在故障时阻断启动或请求  
  → 缓解：完善健康检查、告警、队列持久化与可回滚发布策略。

- **[迁移爆炸半径扩大]** 移除兜底后可能暴露历史配置和依赖问题  
  → 缓解：分阶段发布（local -> canary -> full）、上线前脚本核验、明确回滚流程。

- **[请求时延上升]** 发布失败阻断会在 broker 抖动时拉长请求耗时  
  → 缓解：设置严格超时预算、优化连接池，并监控发布耗时与失败率。

- **[职责边界混乱]** 迁移期可能出现 gateway 与新服务重复承载业务  
  → 缓解：建立接口归属矩阵，按端点逐一迁移与验收。

- **[禁测文件策略带来的质量缺口]** 删除测试后回归风险提升  
  → 缓解：强化启动自检、冒烟脚本与发布验收清单。

- **[适配层过度膨胀]** `cache-kit`/`event-kit` 可能演变为难维护的“万能工具包”  
  → 缓解：坚持最小接口原则，按能力边界拆分模块，禁止混入领域业务语义。

## Migration Plan

1. 明确并发布 Redis key、TTL、RabbitMQ exchange/routing-key 与错误语义规范。
2. 设计并落地 `cache-kit`/`event-kit`，统一封装超时、日志、指标、追踪与错误模型。
3. 在 gateway/history/voice/device 中实现 Redis/RabbitMQ 启动依赖校验，失败即终止启动。
4. 删除核心流程中的 Redis/memory 与 MQ 开关分支，统一改为通过适配层调用。
5. 完成 `voice-service` 与 `device-service` 的入口能力与路由契约。
6. 将 gateway 内部领域处理链路迁移到独立服务，同时保持对外 API 契约不变。
7. 将 gateway 路由配置切换为全量转发到领域服务，仅保留策略与流量中间件。
8. 删除现有 `*_test.go`，并以运行时冒烟/核验脚本替代阶段性质量门禁。
9. 按 canary 逐步放量，持续观测依赖就绪率、发布失败率、请求错误率与服务健康度。
10. 收敛并清理过渡期兼容分支，沉淀标准回滚流程文档。

回滚策略：
- 当错误率或依赖稳定性超过阈值时，回滚 gateway 路由与服务镜像到上个稳定版本，并恢复过渡期配置。
