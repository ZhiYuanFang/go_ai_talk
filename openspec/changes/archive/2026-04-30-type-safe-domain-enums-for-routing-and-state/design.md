## Context

当前代码在消息路由键（`routing_key`）、状态机状态、`target_type`、`mode`、`event type` 等关键域值上大量依赖裸字符串比较（`==`、`HasPrefix`、`switch string`）。这使得跨模块协作时容易出现拼写偏差、语义重复定义与难以发现的运行期错误。随着 outbox + MQ + 缓存投影链路扩展，领域值治理需要从“约定式字符串”升级到“类型化枚举 + 校验注册”。

约束：
- wire 层（DB 字段、MQ 路由键、JSON 字段）仍需兼容字符串。
- 变更需渐进迁移，避免一次性破坏现有调用点。
- 不引入新外部依赖，优先使用现有包结构。

## Goals / Non-Goals

**Goals:**
- 为核心领域值提供统一类型定义与常量集合，减少散落裸字符串。
- 在 outbox 与发布链路引入路由键白名单校验，拒绝未注册键。
- 在 service/controller 层统一使用枚举类型进行分支判断，保持日志与错误语义一致。
- 提供字符串与枚举的双向适配，保证协议兼容。

**Non-Goals:**
- 不改变现有数据库字段类型和消息协议格式。
- 不要求一次性消灭所有字符串文字（如日志文案、自由文本配置）。
- 不引入代码生成器或 DSL。

## Decisions

1. 采用“类型别名 + 常量 + Parse/Validate”模式  
   - 例如：`type RoutingKey string`，配套 `IsValid()`、`ParseRoutingKey(string)`。  
   - 原因：保留字符串兼容性且提供编译期约束。

2. 路由键集中注册到平台层  
   - 在 `eventkit` 或 `contracts` 下提供路由键注册表，写入 outbox 与发布前强校验。  
   - 原因：路由键属于跨模块契约，应集中治理。

3. 状态/模式/目标类型按领域就近定义  
   - `mode` 和 `target_type` 放到 voice/domain，状态机状态放到对应业务包。  
   - 原因：避免平台层承载业务语义，保持边界清晰。

4. 渐进迁移策略  
   - 第 1 阶段：新增类型与适配函数，保留旧字符串入口；  
   - 第 2 阶段：核心调用点切换为枚举；  
   - 第 3 阶段：收敛旧入口并加 lint 规约。  
   - 原因：降低一次性改造风险。

## Risks / Trade-offs

- [迁移期双入口导致复杂度上升] → 通过弃用标记与阶段性清理任务控制窗口。  
- [校验过严导致旧消息被拒绝] → 提供兼容白名单与灰度开关，先观测后强制。  
- [类型定义分散难发现] → 统一命名规范与目录约定（`types.go` + `parse.go`）。  
- [调用点替换不完整] → 增加静态搜索清单与变更检查项（禁止新增裸字符串匹配）。  

## Migration Plan

1. 新增枚举类型与 Parse/Validate，不改调用方行为。  
2. 优先替换 outbox/MQ 路由键写入与消费判断。  
3. 替换 voice 内 `target_type`/`mode` 关键分支。  
4. 替换状态机状态与 event type 判断。  
5. 启用“未注册路由键拒绝”并观察告警。  
6. 清理遗留裸字符串路径并补 runbook。  

## Open Questions

- 路由键白名单是编译时常量硬编码，还是允许配置扩展（建议先硬编码）？  
- 对于历史遗留非法值，是立即拒绝还是先告警后拒绝（建议分阶段）？  
- 是否引入 CI 规则检查新增裸字符串匹配（建议在本变更后续阶段加入）？
