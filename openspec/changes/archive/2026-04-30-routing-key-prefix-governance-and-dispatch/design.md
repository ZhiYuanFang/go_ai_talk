## Context

当前事件路由键已经引入类型化枚举与注册校验，但在 outbox 投影分发等核心路径仍采用“逐个路由键枚举匹配”。随着 `history.record.*`、`device.*`、`voice.task.*` 等事件族扩展，现有写法会持续拉长分支、提高漏改风险。  
本次设计希望在不改变 wire 协议（DB/MQ 仍是字符串）的前提下，引入“前缀常量化 + 白名单校验 + 前缀分发”的治理模型，兼顾可维护性与安全性。

## Goals / Non-Goals

**Goals:**
- 建立统一的路由键前缀常量与命名规范，减少重复字符串前缀定义。
- 在分发链路统一落地“双层判断”：先校验注册合法性，再按前缀归类。
- 降低新增路由键的改动面，避免每次都扩展大量 `switch case`。
- 为后续路由键扩展提供清晰的注册与验收流程。

**Non-Goals:**
- 不变更数据库 `routing_key`/`event_type` 字段类型。
- 不变更 MQ 的 routing key 协议格式。
- 不在本变更中引入动态配置中心式路由注册（保持编译期常量治理）。

## Decisions

1. 前缀常量集中在 `eventkit` 层维护  
   - 采用 `RoutingPrefixHistoryRecord`、`RoutingPrefixDevice`、`RoutingPrefixVoiceTask` 等常量。  
   - 原因：前缀属于跨服务事件契约，不应散落在业务模块。  
   - 备选方案：在各领域包自维护前缀；放弃原因：跨域复用差，容易漂移。

2. 路由键定义采用“前缀 + 后缀”组合  
   - 例如 `history.record.created = RoutingPrefixHistoryRecord + "created"`。  
   - 原因：降低重复片段，新增键时更容易保证一致命名。  
   - 备选方案：全部保留完整字面量；放弃原因：可读性尚可，但长期维护成本更高。

3. 分发链路采用“白名单校验 + 前缀分发”  
   - 第一步：`ParseRoutingKey` 必须通过（拒绝未注册路由键）。  
   - 第二步：基于前缀进入对应领域处理（history/device/voice）。  
   - 原因：仅前缀判断会放过非法键，仅枚举判断会导致分支膨胀，双层策略兼顾安全和简洁。

4. 兼容迁移期间保留旧字符串入口  
   - 对旧入口统一转换到枚举/前缀适配层并输出告警。  
   - 原因：避免一次性清理导致行为波动，支持渐进迁移。

## Risks / Trade-offs

- [前缀定义不当导致路由误归类] → 通过白名单前置校验 + 默认分支保护缓解。  
- [新增事件仅注册未接入分发] → 增加验收清单，要求“注册 + 分发 + 文档”三项联动。  
- [迁移期双入口增加心智负担] → 通过统一适配入口与弃用日志缩短并行期。  
- [过度依赖前缀导致领域边界模糊] → 约束前缀按业务域单向扩展，不允许跨域复用前缀。

## Migration Plan

1. 新增前缀常量并将现有路由键改为前后缀组合表达。  
2. 在 outbox/投影分发路径替换为“双层判断”实现。  
3. 在 repair/reconcile 等边缘链路同步切换分发入口。  
4. 增加 runbook 与验收清单，明确新增路由键流程。  
5. 灰度观察非法路由键告警，确认无误后收敛旧字符串判断分支。

## Open Questions

- 是否需要为前缀映射增加自动化校验（如 CI 静态检查）以阻止遗漏分发接入？  
- `voice.task.*` 是否在本阶段一并接入投影分发，还是仅完成前缀治理与保留分支？  
- 是否需要为“仅注册未消费”的路由键建立显式告警指标？
