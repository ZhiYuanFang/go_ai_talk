## Context

当前项目在 OpenSpec 变更文档上存在中英文混用现象，导致提案评审、设计讨论、任务拆解时的理解成本上升。虽然已经在 `openspec/project.md` 中加入中文化约束，但仍需通过本次变更将规则固化为可执行的规格与任务，确保后续新增变更自动遵循统一语言规范。

## Goals / Non-Goals

**Goals:**
- 将 OpenSpec 文档产物统一为中文表达，覆盖 proposal、design、specs、tasks。
- 明确“中文为默认、英文标识例外”的写作边界，减少执行歧义。
- 形成可检查、可执行的任务流程，保证后续变更持续合规。

**Non-Goals:**
- 不改动业务代码逻辑与运行时配置。
- 不引入新的文档生成工具链或第三方依赖。
- 不对历史已归档文档做批量翻译改写。

## Decisions

1. **统一中文输出范围**
   - 决策：所有新增 OpenSpec 工件均使用中文叙述性文本。
   - 理由：统一团队沟通语言，降低评审门槛。
   - 备选：仅 proposal 使用中文，其他工件不限语言。
   - 不采纳原因：跨工件会再次出现语言割裂，影响追踪与维护。

2. **保留必要英文技术标识**
   - 决策：环境变量、路径、接口、协议关键词等可保留英文原文。
   - 理由：避免关键技术标识被翻译后失真。
   - 备选：所有词汇完全中文化。
   - 不采纳原因：会削弱可执行性，增加实现歧义。

3. **通过规范+任务双层约束落地**
   - 决策：同时新增规格要求与实施任务，保证规则可落地而非口头约定。
   - 理由：仅靠 project 上下文易被忽略，规格与任务可持续追踪。
   - 备选：只更新 project.md。
   - 不采纳原因：缺少显式验收路径和实施闭环。

## Risks / Trade-offs

- **[历史惯性导致执行不一致]** 团队仍可能沿用英文模板  
  → Mitigation：在任务中加入检查项，并在评审入口明确拒收不合规文档。

- **[术语翻译不统一]** 同一概念出现多种中文表达  
  → Mitigation：在项目上下文中维护术语约定，必要时附英文原词。

- **[规则过严影响效率]** 快速讨论阶段可能先产出英文草稿  
  → Mitigation：允许草稿阶段临时英文，但进入变更仓前必须中文化。

## Migration Plan

1. 将“文档必须中文”约束纳入本次变更 proposal/design/specs/tasks。
2. 增加规格定义，明确中文默认与英文例外边界。
3. 增加任务清单，约束后续变更流程中的语言合规检查。
4. 在后续 `/opsx-propose` 与 `/opsx-apply` 执行时按本变更规范验收。

回滚策略：
- 若规则执行阻力过大，可临时放宽为“proposal/design 必须中文，specs/tasks 逐步迁移”，再分阶段收紧。

## Open Questions

- 是否需要增加自动化文本检查（例如关键词比例）来辅助人工评审？
- 对历史未归档但仍活跃的英文变更，是否需要补做中文化迁移任务？
