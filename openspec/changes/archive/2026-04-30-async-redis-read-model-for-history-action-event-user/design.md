## Context

当前系统在 `history/action/event/user` 相关读取中，存在 DB 直查、history 远程调用与部分缓存并存的状态，读取入口不统一。语音链路中 DeepSeek 在构造 prompt 时需要最近历史与用户画像，若命中 DB/远程接口，会放大整体响应时间并增加抖动。在服务拆分与多实例运行场景下，单纯“写后删缓存”会导致高并发下反复回源，无法稳定提供低延迟读取。

约束条件：
- MySQL 仍是权威数据源，Redis 为读模型。
- 系统已具备 Redis 与 MQ/outbox 基础能力，需复用现有 `cachekit` 与异步基础设施。
- 需要兼容 `local|remote|canary` 路径，不破坏服务边界。
- 异步更新必须具备可观测、可补偿、可回滚能力。

## Goals / Non-Goals

**Goals:**
- 将 `history/action/event/user` 读取统一到“Redis 优先，回源兜底，回填恢复”的读模型模式。
- 将写后缓存维护从“删除缓存”升级为“低延迟异步投影更新”，减少 cache miss 雪崩与回源峰值。
- 让 DeepSeek 所需历史上下文与画像优先从 Redis 获取，降低语音链路响应时延。
- 在多实例并发下提供乱序保护、失败补偿与重建机制，确保最终一致。

**Non-Goals:**
- 不追求 Redis 替代 MySQL 成为权威存储。
- 不在本变更中引入跨域共享缓存写入（各域只维护本域读模型）。
- 不在本变更中一次性重构所有历史遗留 DAO 访问路径，仅覆盖明确范围内的读取入口。

## Decisions

1. 采用“通用缓存能力 + 领域缓存仓储”分层
   - 决策：`cachekit` 只承载通用 Redis 能力（命令封装、观测、错误语义），具体 key 与补丁规则放在 `history/action/event/user` 各自缓存仓储。
   - 原因：避免单一工具类承载业务语义，降低跨域耦合并提升可维护性。
   - 备选：在 DAO 层统一注入缓存。放弃原因是难以表达业务语义与失效边界，调试困难。

2. 采用“异步投影更新 + 读时回源回填”的一致性模型
   - 决策：写 DB 成功后发布缓存投影事件，由异步消费者低延迟 patch Redis；读路径 Redis miss 时回源 DB 并回填。
   - 原因：在保证读性能的同时，避免写路径被缓存更新阻塞；即使异步短暂失败仍可通过回源保证可用。
   - 备选：写后同步更新 Redis。放弃原因是写路径耦合增强，失败处理复杂且影响写延迟。

3. 引入版本戳与乱序保护
   - 决策：按实体维度维护版本（如 `history:ver:<deviceNo>`），异步消费者处理事件时仅在版本合法时应用补丁，旧版本事件跳过并记录。
   - 原因：多实例与重试下事件可能乱序，需避免旧事件覆盖新状态。
   - 备选：仅依赖事件时间戳。放弃原因是时钟偏差与重放场景无法可靠判定顺序。

4. 定义可重建与修复机制
   - 决策：提供定时 reconcile 任务，按采样或全量比对 DB 与 Redis 读模型差异并修复；对补丁失败事件进入重试/死信与人工修复路径。
   - 原因：异步体系不可避免存在丢消息、短故障，必须有恢复闭环。
   - 备选：仅靠 TTL 自愈。放弃原因是无法保证热点 key 在 TTL 内的一致性。

5. DeepSeek 历史读取改为读模型优先
   - 决策：`buildRecentHistory` 等链路先读 Redis 历史投影，再按需回源补齐。
   - 原因：直接命中低延迟读模型可降低 prompt 构造阶段波动。
   - 备选：继续直接走 `DeviceHistory().ListHistory` DB/远程结果。放弃原因是时延与压力不稳定。

## Risks / Trade-offs

- [异步延迟导致短暂旧读] → 通过版本校验、短窗口回源兜底、关键链路可选强制回源开关缓解。
- [事件乱序或重复消费] → 通过版本戳、幂等事件 ID、消费者去重键缓解。
- [缓存结构复杂度上升] → 通过领域仓储封装与统一 key 规范、补丁契约测试缓解。
- [修复任务带来额外资源消耗] → 通过分片采样、限速执行、离峰全量重建缓解。
- [运行期排障成本提高] → 增加命中率/回源率/补丁失败率/版本冲突等指标与告警面板缓解。
