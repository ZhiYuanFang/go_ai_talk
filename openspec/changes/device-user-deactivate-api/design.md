## Context

当前 device 用户域围绕 `wx` 记录提供登录、绑定、画像等能力，但未提供注销入口。业务希望新增单一接口用于账号注销，并明确采用“按 `X-Internal-Wx-Id` 删除 `wx` 表对应单行”的最小实现。

约束：
- 仅允许在 device 域内处理数据，不引入跨服务直连。
- 复用现有控制器与服务分层（`api/v1` → `internal/controller` → `internal/services/device`）。
- 保持统一响应封装与错误码风格，避免新增调用方适配成本。

## Goals / Non-Goals

**Goals:**
- 提供 `POST /device/app/api/user/deactivate` 接口。
- 通过请求头 `X-Internal-Wx-Id` 定位并删除 `wx` 表单条记录。
- 明确删除成功、记录不存在、请求头非法三类语义。
- 维持缓存一致性（删除后失效该 `wxId` 相关缓存键）。

**Non-Goals:**
- 不删除 `user`、`event`、`suggest` 等其他域数据。
- 不引入“软删除”字段与历史归档机制。
- 不在本次变更中新增网关聚合接口或前端交互流程。

## Decisions

1. **接口路径与方法**
   - 采用 `POST /device/app/api/user/deactivate`。
   - 原因：与现有 app 用户域接口风格一致，且便于沿用当前网关/客户端调用模式。
   - 备选：`DELETE /device/app/api/user`；未采用，因当前项目在该域已有大量 `POST` 写接口，短期内保持一致性更稳妥。

2. **身份来源**
   - 使用请求头 `X-Internal-Wx-Id` 作为目标主键来源。
   - 原因：项目现有 device app 用户域已复用该头传递 wx 主键，避免新增鉴权字段。
   - 备选：body 传 `wxId`；未采用，避免被客户端任意构造且与现有模式不一致。

3. **数据操作语义**
   - 执行物理删除：`DELETE FROM wx WHERE id = ?`（框架层等价写法）。
   - 原因：用户明确要求“删除对应 id 的一条记录即可”，实现最小且可验证。
   - 备选：软删除（`status=deactivated`）；未采用，因会引入读路径过滤改造和额外迁移成本。

4. **错误与幂等语义**
   - 请求头缺失/非法：返回参数错误。
   - 目标记录不存在：返回明确业务错误（用于调用方提示“已注销或不存在”）。
   - 重复调用：遵循“记录不存在”语义返回，不隐式吞错。

5. **缓存处理**
   - 删除成功后执行 `wxId` 相关缓存失效（id→unionid、id→deviceNo、unionid→deviceNo）。
   - 原因：避免注销后仍读到旧映射数据。

## Risks / Trade-offs

- [风险] 物理删除后无法在 device 域直接恢复账号关联。  
  → 缓解：通过操作日志和上游重新登录重建机制恢复最小信息。
- [风险] 若调用方重复提交，会收到“记录不存在”错误，可能被误判为失败。  
  → 缓解：在接口文档中明确该语义，并由调用方将其视作终态。
- [权衡] 不做软删除降低改造成本，但牺牲了本地审计可追溯性。  
  → 缓解：后续若有审计要求，可在新变更中引入软删除与审计表。

## Migration Plan

1. 在 `api/v1` 新增 deactivate 请求/响应模型并绑定路径。
2. 在 `DeviceAppUserCtrl` 新增 `Deactivate` 入口，复用头解析逻辑。
3. 在 `internal/services/device` 新增删除方法与缓存失效。
4. 联调验证：
   - 正常删除；
   - 头缺失/非法；
   - 重复删除返回“记录不存在”。
5. 回滚策略：回滚代码版本即可；该接口为新增能力，不影响既有路径。
